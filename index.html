how it works

Three steps, and the last one is a text file.

  1. 01

    Ask by IMDb id + duration

    One lookup per title. No upload, no video, no account — the registry matches what you already have.

    GET /v1/sprites?imdb_id=tt1022603&duration_ms=5705536
  2. 02

    Get a sheet and a VTT

    A WebVTT where every cue is one rectangle inside a packed JPEG sheet. Cues are positional, so slot i is second i × interval.

    00:34:20.000 --> 00:34:30.000
    sheet-320x180-2.jpg#xywh=960,360,320,180
  3. 03

    Crop one tile, in anything

    Web, TV, phone, desktop. Floor lookup is a loop over a list you already hold, and the files never expire, so you can cache them like any other image.

    # last cue whose start ≤ position, or nothing at all

contribute

The people watching fill the gaps.

  1. 01

    A player with contribute on captures one tile per interval as the film plays.

  2. 02

    Every 48 banked tiles flush as one bundle: title block, VTT, sprite sheets.

  3. 03

    The registry merges same-title bundles slot by slot, so coverage grows without anyone re-uploading a film.

  4. 04

    Workers stripe the rest. Until they do, past the bound reads as no preview — never a stale frame.

The playback client is released (v0.1.0); the capture half is built and not in a release yet.

Closed preview APIs want an account, cap your daily lookups and expire their URLs after hours. This one asks for nothing — and you can host it yourself, because it is MIT.

Get a key (only for contributing) 
python3 mint_key.py myplayer    # on the registry host — prints the key once

Scraping previews needs no key at all: sprite sheets and VTTs are public files. Keys only gate POST /v1/contribute and the ingest jobs, and their usage is counted rather than enforced.
